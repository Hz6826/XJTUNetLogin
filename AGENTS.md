# AGENTS.md

Guidance for AI coding agents working in this repository. It summarizes the project, architecture, build/release workflow, conventions, and constraints. Keep this file in sync when adding a subsystem or changing the build.

## Project overview

**XJTUNetLogin** (display name: 仙交网络助手) is a Windows desktop client for the Srun-based campus network authentication portal at Xi'an Jiaotong University. It logs in/out of the campus network, shows online-session details, polls the connection in the background, and can auto-login and auto-start with the system.

- Language: C++20
- UI/network: Qt 6.8+ (`Core`, `Gui`, `Widgets`, `Network`, `Svg`)
- Build: CMake >= 3.21, Ninja recommended
- Primary target: Windows 10/11 x64, MinGW toolchain (CI: Qt 6.8.3 + `tools_mingw1310`, GCC 13.1)
- License: MIT (project), Qt under LGPLv3 (dynamically linked; license texts are shipped in release builds)
- macOS/Linux code paths exist in `AutoStart` but are not fully supported/tested; Android is not implemented

Implemented features: login/logout, connectivity test, online-session info, account storage, tray minimization, auto-start, auto-login, version check, portable mode.

## Build and run

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DXJTU_VERSION=1.0.0
cmake --build build -j
./build/bin/XJTUNetLogin.exe
```

Notes:

- If Qt is not in `PATH`, pass `-DCMAKE_PREFIX_PATH=<Qt>/6.x/mingw_64`.
- `XJTU_VERSION` may contain a suffix such as `1.0.0-rc.1`; CMake extracts a numeric version for `project()` and passes the full string into `AppInfo.h`.
- `windeployqt` runs as a POST_BUILD step on Windows to copy the Qt runtime and plugins into `build/bin`.
- There is no unit-test target. CI validates compilation via `.github/workflows/build-test.yml`.
- Do not commit anything under `build/`, `cmake-build-*/`, `dist/`, `portable/`, or `local/`; see `.gitignore`.

## Architecture and data flow

### Startup

`main.cpp` creates `QApplication`, sets organization/application name, acquires the single-instance lock, installs the app icon, then constructs:

```
SrunClient -> MainWindow -> TrayController
```

After wiring the second-instance signal, it calls `client.startPolling(window.config().pollTimerIntervalMs)` and shows the window. All network work is asynchronous on the GUI thread; there are no worker threads or shared-state locks.

### SrunClient (network/protocol)

`SrunClient` is a signal-driven state machine around a single `QNetworkAccessManager` (system proxy disabled, transfers time out after 12 s):

- `login(username, password, acId, domain)`
  1. First `get_challenge` request without an IP: only used to learn the server-side client IP.
  2. Second `get_challenge` request with that IP: returns the real `token`.
  3. `srun_portal` login request with `hmacMd5(password, token)`, XXTEA-encrypted `info` (`{SRBX1}...`), and SHA1 `chksum`.
  4. Poll `rad_user_info` (3 attempts, 1 s apart) to confirm the session is online.
- `logout(...)`: sends `action=logout` and the domain-qualified username, then polls until `not_online_error`.
- `queryOnline(silent)` / `checkInternet()` / periodic polling of `rad_user_info`.
- Login/logout have an overall watchdog (60 s / 30 s); `cancel()` and `reset()` abort in-flight operation replies and timers.
- Periodic polling is single-flight; network errors, parse failures and unexpected server responses are counted and only mark the UI offline after 3 consecutive failures, while an explicit `not_online_error` marks it offline immediately. A successful poll resets the counter and backfills the local IP when it is still unknown.
- The base portal URL defaults to `http://10.6.21.2`; a user override wins over captive-portal detection, and detected redirect origins are adopted only when no override is set.
- Emits `loginSucceeded/loginFailed/logoutSucceeded/logoutFailed/onlineStatusRefreshed/...` and `logMessage(level, message)` for the UI.

`SrunCrypto` mirrors the portal's JavaScript implementation. In particular, the XXTEA MX expression is the Srun variant, not textbook XXTEA; do not "correct" it without a captured test vector.

### MainWindow (UI/state)

`OnlineState { Unknown, Offline, Online, Busy }` is owned by `MainWindow` and mirrored to the tray via `onlineStateChanged`. Login/logout/auto-login set `Busy`; success/failure returns to `Online`/`Offline`.

- `MainWindow` is intentionally split by concern across the `MainWindow*.cpp` files listed above. Add declarations to `MainWindow.h` and put implementation in the matching file; add new `.cpp` files to `CMakeLists.txt`.
- Tabs: 日志 (log), 在线信息 (online info), 设置 (settings), 关于 (about).
- Auto-login triggers when polling detects offline and the portal is detected, respects a 3-failure cap, and is disabled after a user-initiated logout.
- Closing follows a configurable `CloseAction` (ask/minimize-to-tray/quit); tray quit calls `m_window->close()` so geometry is persisted.
- About page contains version-check UI and the log-sensitive toggle (double-click the app icon).

### Tray / single instance / auto-start

- `TrayController` owns the tray menu/icon and notifications, blinks while busy, and calls `MainWindow::onAuthClicked()` for login/logout.
- `SingleInstance` uses a `QLocalServer` named `<author>-<appName>`; a second process pings the primary and exits, the primary raises its window.
- `AutoStart` writes the Windows `HKCU\...\Run` value (quoted command) and handles `StartupApproved`; macOS/Linux implementations write a LaunchAgent/XDG `.desktop` entry.

### Configuration and logs

`Config` is a JSON object with groups `auth`, `auto`, `ui`, `debug`:

- `auth`: username, password (currently plaintext), acId, domain, baseUrlOverride
- `auto`: autoStart, autoLogin, pollTimerIntervalMs (clamped to 10 s–10 min)
- `ui`: logExpanded, filterHttpLog, currentTab, closeAction, windowGeometry, expandedWindowHeight, themeId (WIP)
- `debug`: logSensitive (hidden; disables log redaction when true)

Storage locations:

- Installed mode: `%APPDATA%\Hz6826\XJTUNetLogin\config.json`, logs in `...\logs\xjtu-netlogin-YYYYMMDD.log`
- Portable mode: if `<exe dir>/config.json` or `<exe dir>/portable.flag` exists, config/logs live next to the executable
- Config saves use `QSaveFile`; a corrupted file is renamed to `config.json.bak` before defaults are used

## Security and logging rules

- **Never log** portal tokens, `hmd5`, `chksum`, `{SRBX1}` blobs, passwords, or full authentication URLs. Route log text through `SrunHttpUtils::redactSecrets` / `SrunClient::maskIfNeeded`.
- `logSensitive` is a debug-only escape hatch; it deliberately writes sensitive data to logs. Do not enable it by default or mention it in user-facing UI.
- Do not add secrets, tokens, or personal data to the repository. `config.json`, `portable.flag`, and `logs/` are git-ignored.
- Known limitations (accepted for now): portal traffic is HTTP; the account password is stored in plaintext in the config file. Do not weaken these further without explicit approval.
- Keep license files under `packaging/LICENSES/`; release CI copies them into `build/bin/LICENSES` and into the portable/installer packages.

## Coding conventions

- C++20, Qt naming/style, 4-space indentation, UTF-8 files (no BOM expected).
- User-visible strings and code comments are Chinese; keep new text consistent with the existing tone. Identifiers and commit subjects are English.
- Prefer `QStringLiteral`, `QLatin1Char`, `QLatin1String`, `QNetworkRequest`, Qt containers, and existing helpers over ad-hoc code.
- Use signals/slots and lambdas with a `this` context. Never block the GUI thread; network calls are asynchronous.
- `QNetworkReply` lifetime: read data/headers/status first, then `deleteLater()`. Use `QPointer` when a reply/callback may outlive the current step.
- Do not use exceptions for control flow; report failures through signals/log levels.
- Do not reorder or rename config JSON keys without a migration/backward-compatibility plan.
- `CMakeLists.txt` is the single source of truth for compiled sources; generated headers/resources must stay in the build directory.

## Build, CI, and release

- `build-test.yml`: runs on pull requests to `main` and `workflow_dispatch`; configures with Qt 6.8.3 + MinGW and builds Release.
- `release.yml`: runs on tags matching `v[0-9]*` or manual dispatch. It validates the version as semver, builds, copies Qt/third-party license texts, creates the portable zip (`XJTUNetLogin-Portable-<version>.zip`), builds the Inno Setup installer, and publishes a GitHub release. Pre-release tags (semver `-prerelease`) are marked as such.
- Version selection: tag `vX.Y.Z` or the `version` input; `-DXJTU_VERSION` is passed to CMake, `AppVersion` to Inno Setup, and the version is embedded in `AppInfo.h` and the Windows VERSIONINFO resource.
- Commit subjects follow the existing style: `fix(scope): ...`, `feat(scope): ...`, `build: ...`, `ci: ...`, `doc: ...`.
- For UI/behavior changes, update `README.md` when the change affects users; keep `AGENTS.md` updated for architectural changes.

## Current gaps / work in progress

- Theme selection is incomplete: `MainWindowTheme.cpp` contains empty stubs, `Config::themeId` exists, and the appearance settings group is not yet wired into the settings tab. `buildUiAppearanceSetting()` is currently unused; do not assume theme switching works until this is finished.
- No unit/integration tests are checked in. If you add tests, wire them into CMake and CI explicitly (the current workflows only build).
- macOS/Linux support is best-effort and untested; installer/release artifacts are Windows-only.
- The main window remains fairly large despite being split across files; prefer extracting new panels/controllers rather than growing `MainWindow` further.
